## 3. 주요 피드백 및 의사결정

| 시점 | 내용 | 적용 결과 |
|---|---|---|
| 역할 분담 | 기본 MVC 연습이 필요한 팀원에게 회원·게시판 배정 | Member, Board 기능별 담당 확정 |
| 브랜치 | `main`에 직접 통합하지 않도록 별도 팀 브랜치 권고 | 개인 브랜치 → `team` PR → 최종 `main` |
| JSP 구조 | View를 `WEB-INF/views`보다 `webapp` 기능 폴더에 두고 forward 사용 | JSP 위치와 링크 재정리 |
| 공통 UI | 페이지별 헤더·관리자 메뉴가 달라지는 문제 | 공통 include와 CSS로 통일 |
| 장애 범위 | 사용자 4XX보다 서버 5XX를 운영 장애로 기록 | `IncidentFilter`는 5XX 중심 기록 |
| Severity | AI가 심각도를 임의 결정하지 않도록 분리 | 사람 정의 규칙으로 등급 결정 |
| AI | AI 입력 자체도 공격 데이터가 될 수 있음 | 프롬프트 위협 검사·마스킹 추가 |
| Security | 방화벽 구현은 교육 프로젝트 범위를 초과 | 탐지·기록·관제·알림에 집중 |
| 솔루션 범위 | Hosting·Payment는 초기 비용과 사업 요건이 큼 | Web Security·SentinelOps 중심으로 축소 |
| 사업 모델 | 제한된 무료 기능 후 유료 확장 | API 구독 기능을 후속 요구사항으로 분리 |
| DB | 여러 SQL과 문서가 분산됨 | 스키마 1개, 샘플 데이터 1개로 통합 |
| 보안 설정 | 실제 DB/API/Slack 정보가 노출될 수 있음 | 실제 설정 제외, example과 환경 변수 사용 |
